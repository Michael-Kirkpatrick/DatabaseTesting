# DatabaseTesting

Experiments exploring PostgreSQL 18 behavior and performance at large scale.

The team-facing conclusions and proposed actions are in
[`results/SUMMARY_REPORT.md`](results/SUMMARY_REPORT.md). Detailed benchmark
analysis remains in [`results/FINDINGS.md`](results/FINDINGS.md). To recreate
the study at full or reduced scale, see [`REPRODUCING.md`](REPRODUCING.md).
The controlled in-place TimescaleDB experiment is documented separately in
[`TIMESCALE_COMPARISON.md`](TIMESCALE_COMPARISON.md).

## Billion-row baseline

[`scripts/load_billion.py`](scripts/load_billion.py) creates a local database
named `database_testing` and fills `benchmark_rows` with one billion rows:

```sql
id         integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
group_id   smallint NOT NULL,  -- uniformly distributed from 0 through 100
data_value smallint NOT NULL,  -- full signed smallint range; intentionally unindexed
start_at   timestamp NOT NULL,
end_at     timestamp NOT NULL  -- from start_at through 30 days later
```

The generated values are deterministic and pseudo-random, making repeated test
databases comparable. Loading is committed in resumable batches. For speed, the
primary-key index is built after all rows have loaded; the identity sequence is
then synchronized so future inserts continue at the next ID.

From PowerShell:

```powershell
$env:PGPASSWORD = '<your local postgres password>'
python .\scripts\load_billion.py
Remove-Item Env:PGPASSWORD
```

The script asks for confirmation before starting. Use `--yes` for unattended
execution. Run `python .\scripts\load_billion.py --help` for smaller row counts,
alternate batch sizes, database names, and other options. If interrupted, rerun
the same command to continue from the last committed batch.

## List-page benchmarks

Create the Python environment once:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements.txt
```

The list-page runner compares fetching 100 rows by itself, fetching 100 rows
plus a separate exact `count(*)`, and fetching 100 rows with
`count(*) over ()`. It records client-visible timings, PostgreSQL JSON execution
plans, buffer activity, table/index sizes, and relevant server settings.
Time scenarios use `tsrange(start_at, end_at, '[]')` for both active-at-an-instant
containment and active-period overlap queries, matching PostgreSQL's range-index
operators.

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\benchmark_list_page.py --list-scenarios
.\.venv\Scripts\python .\scripts\benchmark_list_page.py `
    --scenario group `
    --label no_secondary_indexes
Remove-Item Env:PGPASSWORD
```

Raw JSON plans/timings and CSV summaries are written under `results/raw/` and
ignored by Git.
Do not run benchmarks until the initial billion-row load and primary-key build
have finished.

[`results/system_profile.json`](results/system_profile.json) records the CPU,
memory, storage, operating-system, and observed baseline scan-throughput context
needed to interpret results from this machine.

### Lightweight unindexed baseline

The agreed baseline runs only two representative list pages: an intentionally
unindexed `data_value` lookup and a group-plus-active-time lookup. Each executes
one 100-row page and one exact count. The saved plans use plain `EXPLAIN`
without executing the queries again, and window-count queries are omitted. A
five-minute timeout applies independently to each statement and is recorded as
a benchmark result.

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\benchmark_list_page.py `
    --unindexed-baseline `
    --label unindexed_baseline
Remove-Item Env:PGPASSWORD
```

## Index experiments

[`scripts/manage_indexes.py`](scripts/manage_indexes.py) creates and removes only
the benchmark indexes defined by this project. It reports active maintenance,
prints index-build progress, records build time and index sizes, and refuses to
start a build while vacuum or another index build is active on the table.

Check readiness and available index profiles:

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\manage_indexes.py list
.\.venv\Scripts\python .\scripts\manage_indexes.py status
```

First record the already-existing primary-key performance, then create the
group/list ordering index:

```powershell
.\.venv\Scripts\python .\scripts\benchmark_list_page.py `
    --scenario primary_key `
    --label primary_key `
    --repetitions 20 `
    --skip-window-count

.\.venv\Scripts\python .\scripts\manage_indexes.py create group_order
.\.venv\Scripts\python .\scripts\benchmark_list_page.py `
    --scenario group `
    --label group_order `
    --repetitions 3 `
    --skip-window-count
```

Test ordinary start-time ranges with a B-tree. Keep this index for the
remaining experiments because it models a generally useful production index:

```powershell
.\.venv\Scripts\python .\scripts\manage_indexes.py create start_time
.\.venv\Scripts\python .\scripts\benchmark_list_page.py `
    --start-time-suite --label start_time --repetitions 3 --skip-window-count
```

Then compare each time-range index while retaining `group_order` as the common
list-page index and `start_time` as the ordinary timestamp index. Create one,
run the time suite, and drop it before creating the next:

```powershell
.\.venv\Scripts\python .\scripts\manage_indexes.py create period_gist
.\.venv\Scripts\python .\scripts\benchmark_list_page.py `
    --time-suite --label period_gist --repetitions 3 --skip-window-count
.\.venv\Scripts\python .\scripts\manage_indexes.py drop period_gist

.\.venv\Scripts\python .\scripts\manage_indexes.py create period_spgist
.\.venv\Scripts\python .\scripts\benchmark_list_page.py `
    --time-suite --label period_spgist --repetitions 3 --skip-window-count
.\.venv\Scripts\python .\scripts\manage_indexes.py drop period_spgist

.\.venv\Scripts\python .\scripts\manage_indexes.py create period_group_gist
.\.venv\Scripts\python .\scripts\benchmark_list_page.py `
    --time-suite --label period_group_gist --repetitions 3 --skip-window-count
.\.venv\Scripts\python .\scripts\manage_indexes.py drop period_group_gist

Remove-Item Env:PGPASSWORD
```

Index removal asks for confirmation. Build/drop events are stored under
`results/raw/index_events/`. Query result files include the complete set of
indexes that existed during each run.

### Targeted bitmap-memory check

The single-column GiST baseline produced lossy bitmap plans for the two
group-plus-time exact counts at the installation-default 4 MiB `work_mem`.
Before removing that GiST index, repeat only those scenarios with a session-local
override. This does not modify the PostgreSQL server configuration:

```powershell
.\.venv\Scripts\python .\scripts\benchmark_list_page.py `
    --group-time-suite `
    --label period_gist_work_mem_512MB `
    --work-mem 512MB `
    --repetitions 3 `
    --skip-window-count
```

## Deep pagination benchmark

[`scripts/benchmark_pagination.py`](scripts/benchmark_pagination.py) compares
equivalent 100-row pages using `OFFSET` and keyset (`id > last_seen_id`)
pagination. It resolves the cursor outside the timed keyset query, verifies that
both strategies return identical IDs, alternates execution order between
repetitions, and captures execution plans after timing so plan collection does
not pre-warm the measured queries.

The default group-mode depths are 0, 1,000, 100,000, 1,000,000, and 5,000,000:

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\benchmark_pagination.py `
    --mode group `
    --label pagination_group `
    --repetitions 3
Remove-Item Env:PGPASSWORD
```

Cursor discovery is setup work and is recorded separately, not charged to the
keyset query. In an application, that cursor normally comes from the final row
of the preceding page.

## Concurrent-read benchmark

[`scripts/benchmark_concurrency.py`](scripts/benchmark_concurrency.py) measures
five read-only workloads independently at 1, 4, 8, and 16 simultaneous
connections: random primary-key reads, random-cursor group pages, group counts,
group/active pages, and group/active exact counts. Query parameters are
randomized to avoid measuring one permanently hot page. Each stage has a
three-second warm-up followed by fifteen measured seconds and reports
throughput, median, p95, p99, timeouts, errors, and database I/O counter deltas.

The full matrix takes about six minutes plus any slow query overhang:

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\benchmark_concurrency.py `
    --label concurrency `
    --clients 1 4 8 16 `
    --warmup-seconds 3 `
    --duration-seconds 15
Remove-Item Env:PGPASSWORD
```

For the billion-row evidence run, use separate durations so expensive counts
have enough observations for useful percentiles:

```powershell
$env:PGPASSWORD = '<your local postgres password>'

.\.venv\Scripts\python .\scripts\benchmark_concurrency.py `
    --workloads primary_key group_page group_active_page `
    --label concurrency_pages `
    --clients 1 4 8 16 `
    --warmup-seconds 3 `
    --duration-seconds 15

.\.venv\Scripts\python .\scripts\benchmark_concurrency.py `
    --workloads group_count group_active_count `
    --label concurrency_counts `
    --clients 1 4 8 16 `
    --warmup-seconds 5 `
    --duration-seconds 60

Remove-Item Env:PGPASSWORD
```

The benchmark uses one read-only PostgreSQL connection per client and a
60-second per-statement timeout. Workloads run sequentially, so client counts
do not overlap between stages.

## Count-alternatives benchmark

[`scripts/benchmark_count_alternatives.py`](scripts/benchmark_count_alternatives.py)
compares three inexpensive list-page conventions across group, start-time,
active-at, and overlap filters:

- Fetch 101 rows to report whether another page exists.
- Count at most 10,001 rows and display `10,000+`.
- Use the optimizer's non-executing `EXPLAIN` row estimate.

The exact counts already captured by earlier tests are not repeated by default.
The runner uses a read-only session, five repetitions, a five-minute timeout,
and captures execution plans after timing:

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\benchmark_count_alternatives.py `
    --label count_alternatives `
    --cap 10000 `
    --repetitions 5
Remove-Item Env:PGPASSWORD
```

Use `--include-exact` only when an exact-count comparison has not already been
measured; it can add many minutes per repetition on this dataset.

## Configuration plan survey

[`scripts/survey_configuration_plans.py`](scripts/survey_configuration_plans.py)
uses non-executing `EXPLAIN` to identify which session-local configuration
profiles actually change important plans before any expensive timing run. It
surveys cache assumptions, NVMe/random-I/O costing, parallel worker limits, and
PostgreSQL 18 asynchronous I/O depth against sparse pages, temporal pages and
counts, and deep OFFSET pagination.

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\survey_configuration_plans.py `
    --label configuration_plan_survey
Remove-Item Env:PGPASSWORD
```

All settings apply only to the survey connection and disappear when it closes.
The workload queries are planned but never executed. The resulting plan matrix
is used to select a small set of distinct candidates for actual timing.

## Configuration execution benchmark

[`scripts/benchmark_configuration_execution.py`](scripts/benchmark_configuration_execution.py)
executes only the most informative plan changes from the configuration survey.
The default run compares current defaults with the NVMe-oriented cost profile
for a grouped temporal exact count and a five-million-row `OFFSET` page. It uses
`EXPLAIN ANALYZE` once per combination so execution time, plan, buffers, and I/O
timing come from the same execution:

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\benchmark_configuration_execution.py `
    --label configuration_execution `
    --repetitions 1
Remove-Item Env:PGPASSWORD
```

The five-minute timeout applies independently to each query. All configuration
changes are session-local, and the benchmark session is read-only. Broader
ungrouped temporal counts and parallel-worker profiles are available through
`--workloads` and `--profiles`, but are intentionally excluded from the first
run because they can each consume several minutes.

The runner also exposes `io_64` and `io_128` profiles to time PostgreSQL 18
asynchronous-I/O depth changes without changing plan shape or restarting the
server.

## Temporal join model

[`scripts/load_temporal_model.py`](scripts/load_temporal_model.py) creates ten
million temporal items mapped deterministically onto all one billion existing
`benchmark_rows` (100 contiguous fact IDs per item). Each item receives 1--10
non-overlapping versions, averaging approximately 55 million version rows. The
sole text field, `content`, lives on the version so current and historical text
searches can be compared. Generated documents average roughly 200--250
characters and retain controlled common, medium, rare, phrase, item, and version
tokens.

The initial schema creates only primary- and foreign-key indexes. Temporal GiST,
current-version, group, full-text GIN, and trigram indexes are deliberately left
for measured follow-up phases.

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\load_temporal_model.py
Remove-Item Env:PGPASSWORD
```

The loader commits every 50,000 items, records progress in
`temporal_load_state`, and resumes after interruption when invoked with the same
arguments. `--replace` explicitly drops and recreates only the three named
temporal-model tables.

[`scripts/benchmark_temporal_baseline.py`](scripts/benchmark_temporal_baseline.py)
captures the pre-index baseline for point-in-time and latest-version lookups,
fact-first and item-first joins to the billion-row table, current-version
counts, and rare-text page/count queries. Page-shaped queries run three times;
each broad exact count runs once with a five-minute timeout.

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\benchmark_temporal_baseline.py `
    --label temporal_baseline
Remove-Item Env:PGPASSWORD
```

[`scripts/manage_temporal_indexes.py`](scripts/manage_temporal_indexes.py)
builds and records the size/time of optional temporal and text indexes one at a
time. It refuses to overlap an active vacuum or index build on either temporal
table. The first phase is the parent group B-tree followed by the partial
current-version B-tree; GiST and text indexes remain separate later phases.

The historical full-text phase builds the expression GIN and measures rare
(approximately 0.01%), topic (approximately 1%), and common (approximately 20%)
tokens. It also records a current-version rare-token baseline for comparison
with the later partial current-version GIN.

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\manage_temporal_indexes.py create version_fts
.\.venv\Scripts\python .\scripts\benchmark_temporal_baseline.py `
    --scenarios fts_rare_page fts_rare_count `
                fts_topic_page fts_topic_count `
                fts_common_page fts_common_count `
                current_fts_rare_page current_fts_rare_count `
    --label temporal_full_text_gin
Remove-Item Env:PGPASSWORD
```

After the historical GIN run, build the smaller partial GIN for current-version
search and compare the ordinary ordered plan with an explicit GIN-first page.
The separate 64 MiB run checks whether eliminating lossy bitmap blocks repairs
the one-percent topic count without changing the server-wide setting.

```powershell
$env:PGPASSWORD = '<your local postgres password>'
.\.venv\Scripts\python .\scripts\manage_temporal_indexes.py create version_current_fts
.\.venv\Scripts\python .\scripts\benchmark_temporal_baseline.py `
    --scenarios fts_rare_materialized_page `
                current_fts_rare_page current_fts_rare_count `
                current_fts_rare_materialized_page `
    --label temporal_current_full_text_gin
.\.venv\Scripts\python .\scripts\benchmark_temporal_baseline.py `
    --scenarios fts_topic_count `
    --work-mem 64MB `
    --label temporal_fts_topic_workmem_64
Remove-Item Env:PGPASSWORD
```

To locate the smallest non-lossy memory tier and then exercise full-text search
through the normalized current-version join:

```powershell
$env:PGPASSWORD = '<your local postgres password>'
foreach ($wm in '8MB', '16MB', '32MB') {
    .\.venv\Scripts\python .\scripts\benchmark_temporal_baseline.py `
        --scenarios fts_topic_count `
        --work-mem $wm `
        --label "temporal_fts_topic_workmem_$wm"
}
.\.venv\Scripts\python .\scripts\benchmark_temporal_baseline.py `
    --scenarios group_current_fts_rare_page group_current_fts_rare_count `
                group_current_fts_topic_page group_current_fts_topic_count `
    --label temporal_group_current_fts
Remove-Item Env:PGPASSWORD
```
